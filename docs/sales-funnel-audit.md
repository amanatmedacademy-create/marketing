# Аудит и пересборка модуля «Воронка продаж»

Дата: 2026-08-06

## Текущее состояние

Модуль использует три параллельных представления одной предметной области:

1. `marketing_leads` — маркетинговый лид и атрибуция.
2. `sales_funnel_leads` — отдельная копия лида для канбана.
3. `crm_deals` — нормализованная CRM-сделка.

Настройки «воронок» хранятся в `sales_funnel_boards.columns` как JSON. Лид не принадлежит конкретной доске: каждая доска только фильтрует один общий список `sales_funnel_leads`.

## Критические проблемы

### 1. Воронки не изолированы

Создание второй доски не создаёт отдельную воронку. Один и тот же лид одновременно виден в нескольких досках, если проходит их фильтры.

### 2. Стадии жёстко ограничены

Поле `sales_funnel_leads.stage` допускает только шесть значений:

- `NEW`
- `QUALIFICATION`
- `APPOINTMENT`
- `DIAGNOSTIC`
- `COURSE`
- `LOST`

Переименование колонки меняет только подпись. Создать независимую бизнес-стадию нельзя.

### 3. Дублирование данных

Имя, телефон, источник, сумма, ответственные и статус хранятся в нескольких таблицах. Синхронизация частичная и асимметричная. Возможны расхождения между модулем лидов, воронкой и CRM.

### 4. KPI привязаны к системным кодам

Продажа определяется только стадией `COURSE`, потеря — `LOST`, новая карточка — `NEW`. Пользовательская последовательность стадий не влияет на расчёты.

### 5. Быстрые действия обходят последовательность

Кнопки `BOOK`, `COURSE`, `LOST`, `RESTORE` переводят карточку в фиксированную стадию, независимо от выбранной воронки и её порядка.

### 6. Частичная целостность

JSON-колонки проверяются только на тип массива. База не гарантирует существование стадии, порядок, тип результата, уникальность и невозможность удаления стадии с карточками.

### 7. Недостаточная операционная модель

Нет полноценного журнала переходов по стадиям с длительностью, нет причины перехода, нет SLA стадии, нет позиции карточки внутри колонки.

### 8. UI перегружен

Один экран одновременно содержит глобальные KPI, фильтры, конструктор, канбан, эффективность команды, историю и большую форму лида. Управление воронками теряется на широком канбане.

## Существующее CRM-ядро

В базе уже есть нормализованные таблицы:

- `crm_pipelines`
- `crm_pipeline_stages`
- `crm_deals`
- `crm_contacts`
- `crm_audit_log`

Они уже обеспечивают:

- реальную принадлежность сделки воронке и стадии;
- произвольное количество стадий;
- порядок стадий;
- тип стадии `open / won / lost`;
- вероятность;
- tenant/company scope;
- внешние ключи и триггеры целостности;
- RLS и аудит изменений.

## Целевая архитектура

### Источник истины

- Воронка: `crm_pipelines`
- Стадия: `crm_pipeline_stages`
- Карточка: `crm_deals`
- Маркетинговый профиль и атрибуция: `marketing_leads`
- Ответственные: `marketing_users`
- История: `crm_deal_stage_events` + `crm_audit_log`

### Связи

`marketing_leads.crm_deal_id` связывает маркетинговый лид с CRM-сделкой.

`crm_deals` получает дополнительные рабочие поля:

- `marketing_lead_id`
- `diagnost_user_id`
- `priority`
- `description`
- `lost_reason`
- `next_action`
- `next_action_at`
- `stage_entered_at`
- `paid`

### Новая логика стадий

Стадия является отдельной записью с UUID, а не строковым кодом. Пользователь может:

- создать стадию;
- переименовать;
- выбрать цвет;
- изменить порядок;
- указать тип `open`, `won` или `lost`;
- указать вероятность;
- удалить только пустую стадию;
- перенести карточки перед удалением.

### Новая логика воронок

Пользователь может:

- создать независимую воронку;
- выбрать основную;
- копировать структуру без копирования сделок;
- архивировать пустую воронку;
- переносить сделку между воронками с выбором целевой стадии.

### KPI

KPI рассчитываются по выбранной воронке:

- всего сделок;
- открытые;
- выигранные;
- потерянные;
- сумма выигранных;
- взвешенная сумма по вероятности;
- конверсия;
- среднее время в стадии;
- просроченные следующие действия.

## План перехода

1. Расширить CRM-схему без удаления старых таблиц.
2. Создать историю переходов и серверную функцию безопасного перемещения сделки.
3. Мигрировать `sales_funnel_leads` в `crm_deals` с дедупликацией по `marketing_lead_id` и телефону.
4. Перевести Worker API `/api/funnel/*` на CRM-ядро.
5. Пересобрать frontend вокруг выбранной воронки и динамических стадий.
6. Проверить данные и только затем вывести старые `sales_funnel_*` из активного использования.

## Критерии готовности

- разные воронки содержат разные сделки;
- количество и названия стадий не ограничены;
- удаление стадии и воронки безопасно;
- все переходы атомарны и журналируются;
- KPI соответствуют выбранной воронке;
- лид, чат, звонок и CRM-сделка имеют устойчивую связь;
- typecheck, production build и миграционные проверки проходят;
- старые данные не удаляются до подтверждённой миграции.
